## New for people
- **Bookmarks**: Ctrl+D adds or removes; Ctrl+Shift+O opens a searchable list; **import** the HTML file exported by Chrome, Edge, Firefox or Brave (web addresses only). Private sessions cannot add bookmarks.
- **Search engine choice**: DuckDuckGo (default), Google, Bing, Brave Search, Startpage, Ecosia (More menu, Bookmarks and search engine).
- **History** (Ctrl+H): search, Forget one entry, Clear all. Never records Private or agent sessions or pages classed Sensitive/Secret (banking, health).
- **Downloads list** (Ctrl+J): newest first, finished or not, **Show in folder**. Files are never opened from the list. A Private-session download is listed in memory only.
- **Per-site zoom** (Ctrl+ / Ctrl- / Ctrl+0): the familiar 25%..500% ladder, remembered by site, not remembered in Private/agent sessions or on Sensitive pages.
- **Links from other apps**: a link clicked elsewhere opens in the running JevBrowse (a new tab in the default workspace, never in a Private session); only http/https. **Make JevBrowse your default browser** registers it for the current user and opens Windows Settings; Windows requires you to choose it there. *Remove JevBrowse from the browser list* undoes the registration.

## Security fix: shortcuts and zoom persistence required a real key press, not just a message (independent-review finding)
A page -- or any frame embedded in it, including an ad or a widget -- could call `chrome.webview.postMessage('jev:key:closetab')` (or `bookmark`, `addr`,
any recognized shortcut, or `jev:zoom-in`/`-out`/`-reset`) **directly**, with no key press at all, and the browser would act on it: close the active tab
(losing unfinished work), add or remove a bookmark, move keyboard focus into the address bar, or write a zoom level to disk. The `e.isTrusted` check in the
injected script only protected that one listener; nothing stopped a page calling the same browser API itself.

**Fix:** each renderer generates a random, unguessable token when it is created. It is baked into the host-authored script text before that script is
registered with the page -- never placed on `window` or anywhere a page script can read it -- and every `jev:key:*`/`jev:zoom-*` message must carry the
matching token or it is silently ignored, in the top document and in every frame. A page cannot forge the token because it cannot read the closure that
holds it. Informational signals from content (typing happened, a password field exists, media is playing) are unaffected: they only ever narrow when the
browser keeps a tab awake, never act on the person's behalf, so they were not part of this boundary.

**The platform limit, stated plainly:** WinUI 3's managed `WebView2` control does not expose `CoreWebView2Controller.AcceleratorKeyPressed`, the native,
page-independent keyboard hook a fully host-authenticated fix would use; reaching it needs COM interop this pass did not add, to keep the change bounded.
The token is a strong, verifiable boundary (122 bits of entropy the page cannot read), not literally "the OS says a key was pressed" -- disclosed here
rather than overstated. Verified with real WebView2 (row 24, above) and covered on the code side by the ordering-bug regression it exposed.

## Postmessage-interception fix (the gap CHORD_TOKEN_REVIEW.md flagged as untested)
`PageScript` now captures a bound reference to `chrome.webview.postMessage` as the **first** thing it does in each document, before anything else runs
(guaranteed by `AddScriptToExecuteOnDocumentCreatedAsync`), and every outgoing message uses that captured reference from then on. A page script that runs
afterward and reassigns `chrome.webview.postMessage` to a function of its own no longer sees any of this app's own calls, including genuine, real-key-press
ones -- so it cannot read a token off a real forwarded message and replay it as something more damaging. This was the specific, named, unverified gap in
[docs/security/CHORD_TOKEN_REVIEW.md](../security/CHORD_TOKEN_REVIEW.md); that document is updated alongside this record.

**New negative regression (interaction-pass row 25), mutation-checked, including a genuinely cross-origin frame:** a page and an embedded frame -- on a
different port, a different origin under Chromium's same-origin policy, not the same local server as the page -- each install an interceptor, a real
Ctrl+ zoom is pressed in both the top document and the frame, and the interceptor's own capture log is checked for any real token. Reverting the fix
reliably captures a real `jev:zoom-in|<token>` from BOTH the top document and the frame; with the fix, only the interceptor's own blind replay guesses
appear, none with a valid token, and neither closes the tab nor steals focus. Verified twice: once with a narrow standalone harness driven directly against
the app binary (to iterate quickly without the full 25-row suite), and once in the full official run below.

Building the row itself needed two rounds of fixing first, disclosed rather than smoothed over: a PowerShell quoting bug in the injected page markup (an
un-doubled single quote inside a generated script, which silently produced valid-but-wrong content rather than a hard error), and a click-target
size/position mismatch between the small iframe's CSS viewport and the whole app window's coordinates, which made an earlier attempt at this row pass for
the wrong reason (a coordinate click was missing its target, not because nothing could be captured). Both are fixed in `scripts/interaction-pass.ps1`.

## Local interaction pass (this machine, NOT clean-Windows evidence)
`scripts\interaction-pass.ps1` extracts the ZIP itself, into a fresh uniquely-named folder under its run directory (it no longer trusts a caller-supplied folder), then drives it with real key presses, the mouse wheel and UI Automation, using a fresh data folder and a local web server. Results, with the zip hash, build commit and WebView2 version: [json](0.1.0-alpha.7-interaction-pass.json). **On this ZIP: 20 rows PASS, 1 FAIL, 4 NOT TESTED.** Windows 11 Pro 10.0.26200, WebView2 Runtime 153.0.4234.48.

**The 1 FAIL (row 15, search engine) is Google's own automated-traffic page (`google.com/sorry/...`), not a JevBrowse defect**: this machine had run enough
real Google searches across today's repeated testing that Google itself started challenging the traffic. The search-engine *selection* mechanism this row
also checks (choosing Google, and the choice surviving a restart) is unaffected -- row 15b, immediately after, confirms the choice persisted correctly.
Not rerun to chase a clean pass on an external site's rate limiting, per the standing instruction to keep testing bounded.

Covers everything in the alpha.7 feature set (bookmarks including the real file picker, search engine, history, downloads with Show in folder selecting the
exact file, marking a site Sensitive, zoom including inside an iframe and via Ctrl+wheel, browser shortcuts with the page focused, the address bar after
Enter and while typing, a second copy on the same data folder) plus **row 24, a security negative check**: a page and an embedded frame call
`chrome.webview.postMessage` directly -- no key press, no token -- to try to close the tab, zoom the page, add a bookmark and move keyboard focus into the
address bar; none of it has any effect, and a genuine Ctrl+W immediately afterward still closes the tab as normal. **Row 25** is the new cross-origin
capture/replay check described just above.

**Two real defects found this pass, both fixed in this build:**
1. **The security fix below (an audit finding) initially broke every shortcut and zoom action, real ones included.** The token was being set on the lease
   *after* its script had already been registered with an empty one, so every `jev:key:*`/`jev:zoom-*` message -- genuine or forged -- was silently dropped.
   Caught immediately by re-running this same pass (rows 18, 18b, 18c, 21, 22, 23 all failed); fixed by setting the token before the script is registered,
   inside the same constructor call. This is exactly why a regression needs a build that can fail it: the first version of this fix could not have failed
   any test, because it broke the feature it was meant to secure.
2. The negative-check row (24) itself raced its own attack page on the first attempt and needed the attack's timer lengthened and reordered against the
   report-log reset; its first failure was a false alarm in the test, not the product (address-bar focus legitimately stays where Enter left it, which is
   ordinary browser behaviour, not something the attack caused -- the row now establishes real page focus with a click before judging the result).

**Not verified / limits:** row 19 (default browser: opening that dialog writes to the current user's registry), row 14d (the "already saved" message is
only in the status line, which UI Automation did not expose here -- an accessibility note), the Private-session rows through the UI (covered by the
automated engine check), and rows 3, 5, 7-10, 12, 13 of the checklist (real account, upload, permission prompt, clear data, Private restart, offline,
missing runtime). Row 24 (a page/frame directly sending an untokened message) is same-origin; row 25 (the more realistic threat -- a page trying to
intercept and replay a real message) genuinely is cross-origin, on a different port/origin, and shows the same result. The token mechanism itself does not
distinguish by origin -- it rejects any script that does not know the per-lease token, regardless of where it runs.
**Clean-Windows validation remains outstanding and must be done by a tester on their own machine.**

## Packaged smoke: one open, unrelated, pre-existing flake (engine checks / ClickDownload)
The packaged smoke's engine-checks step (`--additions-check`, run inside the extracted, checksum-verified ZIP) failed reproducibly -- 3 times in a row,
at the exact same point -- with `System.ArgumentNullException: Value cannot be null. (Parameter 'json')`, inside a bench-only helper (`ClickDownload` in
`MainWindow.AdditionsCheck.cs`) that simulates a mouse click via DevTools to test the Private-download prompt. Full trace and reproduction JSON:
[0.1.0-alpha.7-packaged-smoke.json](0.1.0-alpha.7-packaged-smoke.json).

**Confirmed unrelated to the postMessage fix above, by mutation test in both directions**: reverting today's fix reproduces the identical failure at the
identical point; restoring it does not change the outcome. It is not caused by leftover processes from a long testing session either -- a full cleanup of
stray `msedgewebview2.exe`/test-server processes before the third attempt made no difference. An initial attempt at a fix (retrying the script call, since
the tab's `Source` property updates before its DOM is actually ready) changed the symptom to a `NullReferenceException` on the WebView2 control shortly
after, rather than resolving it, and was reverted rather than shipped half-understood; the source tree is back to exactly the committed state
(`git status` clean, full unit suite re-run and passing).

**What this does and does not affect:** it is a synthetic, DevTools-driven verification helper, not the download feature itself -- the interaction pass's
row 16c (a real download, clicked through the real UI, with **Show in folder** selecting the exact file) passed cleanly on this same ZIP. What is NOT
independently confirmed by this run is the Private-session download PROMPT specifically (asked first, Cancel saves nothing, Continue saves) -- that
coverage normally comes only from this now-flaking bench, and interaction-pass.ps1 does not separately exercise it through the real UI. This is a real,
disclosed gap in today's evidence for that one behaviour, not a claim that it is broken.

## Corrective pass (after an independent static review; four findings confirmed and fixed, one mismatch removed)
1. **One copy per data folder.** The single-instance guard used the program's folder while storage used `%LOCALAPPDATA%\JevBrowse`, so copies extracted to different folders could open the same database. Startup, storage and the crash log now share one resolver (`DataLocation`), the guard is keyed by it, and an exclusive lock file in the data folder is held for the life of the process. If a hand-over fails or the lock is taken, the copy stops with a message instead of carrying on. Verified with real processes (a copy started while another process held the folder shows the message and exits with code 1). The default-path equality is unit-tested only: no real run touched `%LOCALAPPDATA%`; the clean-Windows run uses it.
2. **History and zoom follow class changes.** Marking a site Sensitive (and a page turning Sensitive later, for example when a card field appears) now removes that site's saved history and zoom. A Private tab on the same site cannot erase an ordinary tab's history. Mutation-checked (removing the late purge, or the sweep, fails a test each).
3. **Download ownership.** A download's owner (container and workspace) is fixed when the page is created, not looked up when the download ends; an unknown owner is treated as Private (memory only); ending a Private session removes its download names from the list (the files stay). Verified in the engine check (31 steps).
4. **Release publishing.** A package built by one run is no longer what a second run publishes: publishing (`scripts\publish-release.ps1`, or the two-step workflow) refuses unless the zip's SHA-256 equals the hash you tested and matches `SHA256SUMS.txt`, and never attaches symbols. A tag push does nothing. **GitHub Actions is currently blocked by a billing/spending-limit notice on the account, so the workflow's package step could not be re-run and the corrected workflow is untested; the local script was exercised (matching hash passes, another hash is refused).**
5. Registration no longer claims `.htm`/`.html` file associations (the launch path only opens web addresses).
